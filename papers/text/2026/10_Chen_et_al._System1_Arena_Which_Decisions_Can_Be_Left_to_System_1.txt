System1-Arena: Which Decisions Can Be Left to System 1?
Tianyu Chen* Xinyang Liu* Ruyi An Zhendong Wang Mingyuan Zhou †
The University of Texas at Austin
Abstract
Large language models (LLMs) often make dis-
crete decisions, such as flagging phishing or
escalating to a human.System-1 models, such
as Jev and the OpenAI Decisions API, return
probabilities over options in a single forward
pass, whileSystem-2approaches generate rea-
soning steps. Which decisions can System-1
models handle, and which require generative
reasoning? We introduce System1-Arena, a
benchmark that gives all models the same deci-
sion requests and scores their probabilities. It
contains 92k questions across 105 tasks from
268 public sources, in four groups: text classifi-
cation and knowledge, applied decisions, evalu-
ation and control, and agent and action. It also
includes 138 closed-loop environments, from
web shopping and SWE-bench coding control
to robotics, games, and driving; in real-time
mode, the world evolves while a model decides.
We evaluate 30 models: 7 closed LLMs, 13
open LLMs read at the answer token, and 10
System-1 models. The largest System-1 mod-
els match or exceed fast closed LLMs in non-
agentic accuracy, with better-calibrated proba-
bilities at one-quarter of the latency. A reason-
ing LLM is the most accurate, at about70× the
cost of a fast LLM. In closed loops, large open
LLMs succeed most often (up to 32.9%); small
System-1 models rarely succeed.

System 1supports fast, automatic judgments,
whileSystem 2supports slower, deliberate reason-
ing (Kahneman, 2011). LLM studies often use this
distinction to describe shorter and longer reasoning
by the same model (Yu et al., 2024; Ziabari et al.,
2025; Zhang et al., 2025c). Here, we study models
that directly predict probabilities for discrete deci-
sions. Jev (TypeSafe AI, 2026) and the Decision-
2.0 family (vLLM Semantic Router Team, 2026)
accept a state and typed questions. Question types
include yes/no, multiple choice, and ordered scales.
These models return a probability distribution for
each question in one forward pass, without gen-
erating text. The OpenAI Decisions API (Ope-
nAI, 2026a) provides the same decision interface
through GPT-6 Luna, and Microsoft-Decision-1
(Microsoft, 2026) provides it through a post-trained
Qwen3.5-9B. These systems can respond within a

few hundred milliseconds at low cost. In our runs,
Jev cost about $0.05 per 1,000 requests. Probability
estimates support decision thresholds, calibration,
and rules for escalation to a human.
This raises a central question: which decisions
can System-1 models handle, and where do gener-
ative LLMs perform better? Existing benchmarks
provide limited evidence. JevBench (Benchmark
Heaven, 2026) and ReflexBench (Brida AI, 2026)
each contain only a few hundred synthetic deci-
sions. Their narrow coverage makes model rank-
ings sensitive to task selection. They mainly com-
pare System-1 models and do not include agentic
tasks. These tasks are an important use case be-
cause each decision can affect later actions, and
delays can change outcomes.
We introduce System1-Arena, a benchmark with
92,125 typed questions across 105 tasks from 268
public sources in 16 domains. It also includes 138
closed-loop environments from 18 families. In real-
time mode, the environment continues to evolve
while a model decides. We evaluate System-1 mod-
els alongside open and closed LLMs through a
shared decision interface. Each model family uses
a fixed prompt, and we score the predicted probabil-
ities. System1-Arena follows three design choices.
• Broad coverage.Every model receives the same
decision request for each example: a state and
typed questions. Labels come from test execu-
tion, solvers, experts, annotator distributions, and
resolved events. We preserve the instructions
from each source (Section 3.2).
• More than accuracy.Each model returns a prob-
ability distribution for every question. We report
accuracy and use the Brier score to assess proba-
bility quality. More details are in Section 3.4.
• Agentic tasks.We evaluate individual agent de-
cisions and success in closed-loop environments.
In real-time mode, the environment continues to
evolve for the duration of each model call, using
that model’s measured latency (Section 3.3).
We evaluate 30 models: 7 closed LLMs, 13 open
LLMs evaluated through answer-token probabil-
ities, and 10 System-1 models. On non-agentic
tasks, Jev and Decision-2.0-Vega-27B reach 72.6%
and 73.0% accuracy, respectively, compared with
71.2% for GPT-6 Luna. They also produce better-
calibrated probabilities at lower latency than fast
closed LLMs (Figure 1). The performance gap
between the best System-1 models and the best
LLMs is smallest on filtering, grouping, ranking,
retrieval, and dialogue tasks. System-1 models re-
main less accurate on knowledge and forecasting
tasks (Figure 3).
Reasoning LLMs achieve the highest accuracy.
Claude Opus 5.5 reaches 81.1%, at about 70×
the cost of a fast LLM. Explicit reasoning also
improves open LLM accuracy. With a few hun-
dred reasoning tokens per question, Qwen3.8-27B
reaches 75.6%, exceeding Jev’s accuracy but pro-
ducing less-calibrated probabilities (Figure 4).
In agentic tasks, some models perform well on
single-step decision tasks but struggle with long-
horizon tasks. Decision-2.0-Vega-27B, Jev, and
Qwen3.5-9B all achieve 67.8% accuracy on single-
step tasks. On long-horizon tasks, Gemma-4-31B
achieves the highest success rate at 32.9%. The
four small System-1 models reach at most 3.1%,
showing limited ability to handle long-horizon plan-
ning. The OpenAI Decisions API is faster and
better calibrated than GPT-6 Luna, but achieves a
lower success rate on long-horizon tasks.
In sum, we make four contributions. First,
System1-Arena provides a shared decision inter-
face for System-1 models and LLMs, with labels
and instructions linked to their sources. Second,
our real-time protocol advances the environment
during model inference to measure the value of
fast decisions. Third, we provide a method for
obtaining decision probabilities from open autore-
gressive and diffusion LLMs through their answer
tokens. Fourth, our evaluation of 30 models iden-
tifies where System-1 models match LLMs and
where they fall behind.
2 Related Work
System 1 and System 2 in language models.
The dual-process distinction of Kahneman (2011)
is often used to describe how much a language
model reasons before answering. Yu et al. (2024)
distill long reasoning outputs into models that an-
swer directly. Ziabari et al. (2025) align models
toward either end of this spectrum and find that
faster responses perform better on commonsense
tasks, while slower reasoning performs better on
arithmetic and symbolic tasks. S1-Bench (Zhang
et al., 2025c) shows that large reasoning models
overthink simple questions. These studies examine
System 1 and System 2 behavior within genera-
tive models. System1-Arena compares generative
LLMs with a separate class of models that return
decision probabilities without generating text, and
2

identifies which decisions these models can handle.
Typed decision models and zero-shot classifiers.
Zero-shot text classification assigns labels spec-
ified at inference time. Yin et al. (2019) frame
this task as entailment, and Laurer et al. (2023)
train universal classifiers across tasks formatted
as natural language inference. System-1 mod-
els such as Jev (TypeSafe AI, 2026), Microsoft-
Decision-1 (Microsoft, 2026), and the OpenAI
Decisions API extend this interface to multiple
typed questions per input—boolean, choice, and
ordered scores—with a probability for each op-
tion. JevBench (Benchmark Heaven, 2026) and
ReflexBench (Brida AI, 2026) evaluate accuracy,
calibration, robustness, and speed on a few hundred
newly written decisions, mainly comparing System-
1 models. System1-Arena covers 92k questions
with source-provided labels, compares System-1
models and LLMs on the same decision requests,
and evaluates them in closed-loop environments.
Holistic benchmarks, calibration, and cost.
MMLU (Hendrycks et al., 2020), BIG-bench (Sri-
vastava et al., 2022), and HELM (Liang et al., 2022)
evaluate models across diverse tasks using a com-
mon protocol. HELM also reports calibration and
efficiency. The Brier score (Brier, 1950) evalu-
ates probabilistic predictions, while expected cali-
bration error (Guo et al., 2017) measures the gap
between confidence and accuracy. Large models
can produce well-calibrated token probabilities on
multiple-choice questions (Kadavath et al., 2022).
For instruction-tuned models, verbalized probabili-
ties can be better calibrated than token probabilities
(Tian et al., 2023), but can still be overconfident
(Xiong et al., 2023). We use verbalized proba-
bilities for closed LLMs to obtain a full distribu-
tion for each question through their text-generation
APIs. Cost-aware methods route queries among
LLMs of different sizes (Chen et al., 2023a; Hu
et al., 2024). System1-Arena asks which decisions
a System-1 model can handle, informing routing
between System-1 models and generative LLMs.
Interactive and latency-sensitive evaluation.
Most benchmarks for web agents, text games, cus-
tomer support, coding, and reinforcement learning
pause the environment while the model decides.

uation. Kang et al. (2025) show that tailoring model
size and quantization to a latency budget improves
performance in both a trading simulation and a

3 System1-Arena
3.1 Decision requests
We represent every static example and environment
step as adecision request r= (s, Q) (Figure 2).
The state s contains a small set of named text fields.
Examples include a message, a code diff with its
commit message, or a rendered web page. The
questionsQ={q 1, . . . , qm}share this state.
Each question isboolean(yes/no),choice(2–
255 options with exactly one correct answer), or
score(2–10 ordered levels). Score levels can rep-
resent a grading rubric. Each question includes
instructions, and each option includes a descrip-
tion, so models need no dataset-specific prompt. A
model returns a probability distribution over the
options for each question. The reference answer
is a hard label or, when available, a distribution
provided by the source.
System-1 models receive the request directly.
LLMs receive a text version through a fixed prompt
for each model family (Appendix A). Section 4
explains how we obtain the option probabilities p
from each model.

3.2 Non-agentic decisions
This component contains 78,362 questions across
13 domains and 87 tasks (Table 3). Each task cov-
ers one type of decision and draws on one or more
public sources. Examples include deciding whether
a message is phishing or whether a patch fixes an
issue. The domains cover text classification, knowl-
edge, professional tasks, retrieval, structured data,
code, and forecasting. They also cover dialogue,
batch processing, LLM-as-judge, safety, routing,
and subjective judgments. Appendix C lists the
sources for all benchmark tasks.
Labels and instructions.All labels come from
the original sources; we do not create new labels.
They include test results, solver outputs, resolved
events, expert annotations, annotator distributions,
and original dataset labels. When a source provides
instructions or annotation guidelines, we preserve
their wording or adapt them to the decision-request
format. Otherwise, we write instructions based
on the source’s labeling criteria. This keeps the
instructions consistent with how the labels were
assigned. Appendix B describes the procedure.
3.3 Agentic tasks and environments
Agentic tasks require a model to choose a sequence
of actions to achieve a goal. Each action changes
the state observed at the next step, so success de-
pends on decisions throughout an episode. We
include 138 environments from 18 families and 22
benchmark suites. They cover web shopping, cus-
tomer service, coding, robotics, games, and driving
(Appendix D).
To support System-1 models on long-horizon
tasks, we use a fixed, task-specific harness. At each
step, it converts the current state and interaction his-
tory into text and presents the available actions as
typed questions. It executes the highest-probability
option for each question and obtains the next ob-
servation. We represent free-form outputs, such
as search terms, tool arguments, and patches, as
candidate choices. Actions come from the original
benchmark’s action space, and all models use the
same harness and environment. For environments
with a success criterion, we report the mean success
rate, giving each environment equal weight.
Single-step tasks.We separately evaluate indi-
vidual agentic decisions using recorded trajectories
and fixed states from games and embodied tasks.
Each example provides a fixed state and interac-
tion history. Questions ask which action to take,
whether a proposed step is correct, or whether the
task is complete. We score the answer against a
reference without continuing the interaction. Refer-
ences come from expert demonstrations, execution
checks, solvers, recorded outcomes, or source an-
notations. These tasks measure decision quality for
a given state and history.
The full single-step collection contains 13,763
questions across 18 tasks. It includes 6,943 ques-
tions about agent steps, 3,828 about games, and
2,992 about embodied and robotics tasks (Table 3).
Together with the non-agentic component, these
tasks account for all 92,125 questions and 105 tasks.
Our single-step model comparison uses only the
agent-step subset (Table 2). This subset contains
3,481 recorded steps and 6,943 questions across
seven tasks. The static game and embodied tasks re-
main part of the benchmark but are excluded from
this comparison.
Harness difficulty check.We check whether the
harness makes the original task too easy. We flag
environments where a uniform-random policy suc-
ceeds in at least 20% of episodes or models gener-
ally achieve at least 90% success. For flagged en-
vironments, we removed assistance or reduced the
decision budget. For example, we limited the bud-
get to twice the shortest solution length in BabyAI,
MiniHack mazes, and Baba Is AI. A scripted policy
confirms that each adjusted task remains solvable.
Real-time mode.In Atari, Doom, driving, and
quadrotor environments, the world continues to
evolve while the model decides. For each decision,
the environment advances by the model’s measured
median latency and continues to execute its previ-
ous action. Slower models therefore act on older
observations. This makes response time part of
task performance (Appendix D).

Protocol.Questions with failed calls, unusable
responses, or refused inputs receive no accuracy
credit. In environments, the harness executes the

Microsoft-Decision-1, OpenAI Decisions API, and

ferent closed-loop success rates.Model rank-

6 Conclusion
System1-Arena asks one question of every deci-
sion: can it be left to a fast model that answers
with calibrated probabilities in a single forward
pass, or does it still need a generative LLM? Pos-
ing the same typed requests to 30 models makes the
question measurable. The answers are encouraging
for System 1 on most static decisions, where the
largest System-1 models match fast closed LLMs
with better-calibrated probabilities at a quarter of
the latency, and sobering where the best accuracy is
needed, which a reasoning LLM delivers at about
70 times the cost. In closed loops, large models
8

succeed most often, step accuracy does not predict
loop success, and small System-1 models lack the
planning that a loop needs. We hope the bench-
mark helps decide, decision by decision, where
deliberation is worth its price.
7 Limitations
Labels are inherited from the sources, so their noise
is inherited too; tier-C instructions were written by
us; and many sources are public and several years
old, so some inputs may have been seen in training.
The closed LLMs, Jev, Microsoft-Decision-1 and
the OpenAI Decisions API were called through
online services, so their latency includes the service
and the network, and cost reflects the prices on the
days of the runs. The models that sample their
answers got one draw per request, so run-to-run
variation is not measured.
8 Ethical Considerations
System1-Arena reuses public datasets and environ-
ments under their licenses (Table 4); sources whose
terms do not allow redistribution are rebuilt locally
by a loader and are not redistributed. Toxicity, hate-
speech, and safety tasks contain offensive or unsafe
text by design; we keep these inputs as their cre-
ators released them and add no new personal data.
A high score on the benchmark does not show that
a model is fit for decisions with legal, medical, fi-
nancial, or safety consequences, where errors can
harm people and human review remains necessary.

A LLM Prompts
The closed LLMs and the open LLMs get differ-
ent prompts, because we get their probabilities in
different ways (Section 4). Each family has one
fixed prompt, and no model gets a prompt that we
tuned for it. Both examples below use the same
request of the date-arithmetic source (knowledge
and reasoning).
A.1 Closed LLMs: verbalized probabilities
A closed LLM writes its probabilities as numbers
in a JSON object. We do not read the probabilities
of its tokens. All closed LLMs get the same two
messages, and one request with all its questions is
one call. The system message is:
You are a classifier. Read the input
and answer every question. For each
question give a probability for the
allowed options; the probabilities of
one question must sum to 1. Reply with
a single JSON object and nothing else.
The user message gives the request:
Input:
{
"date": "1968-03-18"
}
Questions:
- "date" (choice): Which date is 80 days
after the given date?
- "A": June 6, 1969
- "B": July 6, 1968
- "C": June 5, 1968
- "D": June 6, 1968
Reply with JSON of the form
{"<question>": {"<option id>": <probability>,
...}, ...}.
Options you leave out get probability 0.
(We break the two long lines here for the column
width; the model gets them unbroken.) A boolean
question lists the options "true" and "false". A
score question lists its levels as "0", "1", . . . with
the description of each level.
A.2 Open LLMs: probabilities of label tokens
An open LLM does not write probabilities. It gets
one question per prompt, and we read the proba-
bility of each label token at the position where the
answer starts (Section 4). The chat template of the
model contains the two messages and opens the re-
ply of the assistant; with no reasoning, the prompt
ends there. The system message is:
You are a classifier. Read the input
and answer the question. Reply with the
label of your answer only.
The user message gives the state and one question:
Input:
{
"date": "1968-03-18"
}
Question: Which date is 80 days after the
given date?
Options:
A. June 6, 1969
B. July 6, 1968
C. June 5, 1968
D. June 6, 1968
Reply with the label of one option.
(We break the long line again.) We read the log-
probabilities of the tokens A, B, C and D. A boolean
question ends with “Reply yes or no.”, and we read
yes and no (with Yes and No added in). A score
question lists its levels as 0., 1., . . . and ends
with “Reply with the number of one level.” Dif-
fusionGemma gets the same two messages. GPT-
OSS gets them in its own chat format, and we read
the labels after its reasoning message.
A.3 System-1 models
Jev gets the request through its native interface:
the state as JSON and, for each question, its type,
instructions and option or level descriptions. The
OpenAI Decisions API gets the same request: the
state is the JSON text that the LLMs see, a boolean
question is a predicate, a choice question keeps its
options and their descriptions, and a score ques-
tion gives each level the label 0 to n−1 and its
description. The API returns P(true) for a predi-
cate and a distribution over the options or levels
for the other types. OpenRouter’s Decisions API
serves Microsoft-Decision-1 and takes requests in
the same format as Jev’s interface; only the type
name of a boolean question differs ( noul). The
API returns P(true) for a boolean question and a
distribution over the options or levels for the other
types. The other System-1 models get the request
through the code that their authors released.
B Evaluation Details
Static tasks.Each task has about 500 requests,
split evenly across its sources, sampled with a fixed
seed and stratified by label; tasks that target rare
events are balanced instead. Some sources produce
several requests per record (a vulnerable function
and its fixed version, two orderings of a pairwise
comparison); these share a group identifier for the
pair metric. 4,425 requests carry a soft label, such
as the share of 100 annotators who chose each
label. Tier C instructions (33% of the requests) are
written by us from the source’s criteria. There is no
shared input budget: every request is sent in full.
24

The 2,607 requests whose licenses do not allow
redistribution are rebuilt locally by loaders.
Metrics.With k samples per request, accuracy
is avg@k, and maj@k takes a majority vote; this
paper uses k= 1 . The expected calibration error
(Guo et al., 2017) uses the confidence of the top op-
tion with 10 equal-mass bins. Tasks whose requests
rank candidates for a query also report NDCG of
the expected score levels, and paired requests report
pair accuracy, the share of pairs with all questions
correct. A question without an answer counts as
the uniform distribution for the Brier score, the
expected calibration error and NDCG.
Reading open models.For a boolean question,
the probability of the label yes includes the token
Yes, and no includes No. A question with more than
26 options gets number labels of several tokens
(“001” to “151”); we score them on a prefix tree
of their tokens, and zk is the sum of the token log-
probabilities. We log the probability mass on the
labels to check that the answer position is correct.
GPT-OSS writes a reasoning message of at most
4,096 tokens (2,048 on the agentic tasks) at its
lowest effort, and we read the labels at the first
token of its final message. For DiffusionGemma,
the answer label is one slot of the denoising canvas,
all other canvas positions are fixed, and one read-
only denoising step returns the label probabilities
at the slot. All open models run with vLLM (Kwon
et al., 2023).
Thinking budgets.Four open LLMs (Qwen3-
8B, Qwen3.8-27B, Gemma-4-26B-A4B and Dif-
fusionGemma) answer every question of the non-
agentic tasks in their thinking mode. Each question
gets one thought, sampled with the model’s own
generation settings and written up to 2,048 tokens;
the model is not told its budget. For a budget B
of 0, 128, 256, 512, 1,024 or 2,048 tokens, we
keep the first B tokens of this thought (or all of it,
if the model ended it sooner), close it as the chat
template closes a thought, and read the label prob-
abilities at the next position as in Section 4. The
budgets therefore differ only in where one sam-
ple is cut. DiffusionGemma writes its thought in
blocks of 16 tokens and is read at the first answer
token. Figure 4 starts each curve at thinking off,
the setting of Table 1. We also ran budget 0, the
thinking prompt with an empty thought. It gener-
ates no tokens either, but its prompt differs from
thinking off: Qwen3.8-27B adds a line that sets
the reasoning effort, and Gemma-4-26B-A4B and
DiffusionGemma add a thinking flag and an empty
thought channel (for Qwen3-8B the two prompts
are the same string). Under this prompt, the mod-
els often want to go on thinking instead of answer-
ing, and budget 0 is less accurate than thinking
off by 2.1 points (Qwen3.8-27B), 3.6 (Gemma-4-
26B-A4B) and 13.5 (DiffusionGemma). The 95%
intervals come from a paired bootstrap stratified by
source. The four models used 58.8 GPU-hours on
H100 GPUs for all budgets.
Inputs.We do not shorten an input, with two
exceptions: the Laya library cuts an input to 512
tokens, and for CLM we keep the last 2,048 tokens
of each text, the end that its training keeps.
Calls and episodes.A call that fails in transport
or on a rate limit is retried. A reply that cannot
be parsed, and a request that a model refuses, are
final, and a model never gets a second sample. The
refusals of the OpenAI Decisions API are deter-
ministic: the same request sent again gets the same
refusal. An environment allows its own number of
decisions per episode and has 1 to 114 episodes.
Of the 138 environments, 128 report success or
failure and 10 only a score; one of the 128 (the
coding controller with a GPT-4.1 mini proposer)
was played only by Jev, so the loop success is a
mean over 127 environments. The static games and
embodied tasks of the agent and action group are
not part of this evaluation.
Services and hardware.We call the closed
LLMs through GitHub Copilot for the non-agentic
tasks; for the agentic tasks, we call the two Luna
models through Amazon Bedrock. Non-agentic
Copilot costs use the recorded rate of $0.01 per
usage credit. Copilot charges each model its listed
credits per million input and output tokens; a GPT-
5.6 model costs twice as many credits per input
token as the GPT-6 model of the same tier (400 for
GPT-5.6 Sol, 200 for GPT-6 Sol). Jev runs through
the Vercel AI Gateway. We call the OpenAI Deci-
sions API (public beta, October 2026) directly; its
cost is the list price of $0.10 for one million input
tokens, and it does not charge for output. We call
Microsoft-Decision-1 through OpenRouter’s Deci-

D Closed-Loop Environments
Our environments come from agent benchmarks
for the web (MiniWoB++ (Shi et al., 2017; Liu
et al., 2018), WebShop (Yao et al., 2022)), text
games (TextWorld (Côté et al., 2018), Jericho
(Hausknecht et al., 2019), ScienceWorld (Wang
et al., 2022), ALFWorld (Shridhar et al., 2020)),
support agents (τ 2-bench (Barres et al., 2025)), cod-
ing agents (SWE-bench (Jimenez et al., 2023)), the
long-horizon games of BALROG (Paglieri et al.,
2024), and control and game simulators built for
reinforcement learning (MuJoCo (Towers et al.,
2024; Todorov et al., 2012), Meta-World (Yu et al.,
2019), the Arcade Learning Environment (Belle-
mare et al., 2012), ViZDoom (Kempka et al., 2016),
highway-env (Leurent, 2018), and PyFlyt (Tai et al.,
2023)). Table 5 lists every environment. A failed
answer falls back to a fixed default action. Out-
comes are the simulator’s own: success where the
task defines it, and otherwise its return, score or
progression.
Coding controller.The coding controller turns
SWE-bench Verified (Jimenez et al., 2023; Ope-
nAI, 2024) into decisions. A fixed proposer inside
the environment writes the candidate next actions
(code views, test runs, patches, a revert); the model
picks one, which runs in the task’s official con-
tainer, or submits the changes so far, which SWE-
bench’s own tests grade. The scripted proposer
offers the reference patch among failing patches
from public submissions, so the task is to recognize
the right fix and stop; the GPT-5.6 Luna proposer
writes five actions without reasoning and never the
reference patch, so the decisions have to steer it
toward a fix. This proposer is the only LLM inside
a harness.
Realtime mode.Each model m is charged a
fixed latency Lm per decision: its median latency
per request, measured on an idle A100 GPU and
rounded to 10 ms. While a decision is pending,
the environment advancesround(Lm/∆t) steps of
length ∆t with the previous action held. A fixed
latency, rather than the measured wall-clock time,
keeps episodes reproducible. A two-car intersec-
tion extends this mode to several agents, each con-
trolled by an independent call of the same model.

the strongest positive torque; in Meta-World the
